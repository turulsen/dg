# Delta Green Agent Hub

Player- and Handler-facing tools for a Delta Green campaign, published as a static site via GitHub Pages, installable as an offline-capable PWA.

**Live site:** enable GitHub Pages on this repo (Settings → Pages → Deploy from branch → `main` → `/ (root)`) and it'll be served at `https://<your-username>.github.io/<repo-name>/` — this repo is `dg`, so `https://turulsen.github.io/dg/`.

## What's here

`index.html` is a three-clearance landing page (after a one-time, session-gated boot-splash animation): **Agent**, for players, **Friendly**, for one-shot players with a ready-made pregen, and **A-Cell**, for the Handler, password-gated. The three are aged manila folders lying fanned on the black page, labelled by hand (since v3.4.0). Both lead into a shared "manila folder on a desk" visual system (`assets/theme-folder.css`, with the patina as CSS tokens) used across every hub page; the Field Notes notebook shares that same paper/ink/typewriter system directly rather than having a separate look.

### Field Notes notebook

Live since v2.1.0. A leather notebook (`assets/field-notes.js`/`.css`) carried on every player page, and inside the Hub shell (`hub.html`) one notebook for the whole tab. Closed, it's a small notebook in the corner of the screen (on a phone, a notebook button and a dice button). Open, it's a two-page book with real page turns:

- **Left page, the card holder:** three pockets for the Agent File, Field ID and Requisition cards (since v3.2.0 the Agent File card flips through the player's Agents: ‹ 1 of 3 › on its pocket, a swipe, or the same arrows in the phone's header), then the radio (a pager face on the Table Radio engine) and the dice tin. On a phone the radio opens from the notebook's header instead.
- **Right page, a tabbed booklet:** Agent File (the playable sheet, the same one as on Agent Hub; see Agent File below), Field ID (the Agent's credential card; *Make Field ID* opens the Fabricator across both pages), Requisition (the full form lives only here), Dice, Notes, Evidence (filterable by Operation and sortable by date or title, the sort remembered on the device and shared with Agent Hub's list; tap a photo to see it full-screen with pinch and double-tap zoom, a PDF opens in the browser's PDF viewer), Rules (opening with The Mission & Standing Orders, the five priorities in our own words) and Settings (Cover Identity, the boot splash, and the sheet's own settings).
- **Split** (desktop): the brown tab under Settings puts the Agent File on the left page, in place of the card holder, with Notes (the whole Notes page), Evidences, Rules or Settings on the right. A roll from the left page turns the right one to the Dice Roller. Remembered on the device.

It replaces the floating Table Radio pill, the Dice Roller panel, the sheet's settings cog and its phone Notes button, and drives their existing engines rather than duplicating them. Split View (sheet and Notes side by side) is retired: its buttons are hidden wherever the notebook runs. A-Cell has no notebook; the Handler keeps the radio pill and dice panel there. The Handler's dice panel shows Live Rolls from every Cell, with a filter at the top for one Handler's Cells (each Cell's Handler field) or a single Cell, remembered on each device. Players only ever see their own Cell's rolls: the Handler's feed exists on A-Cell alone, so a shared tablet logged into A-Cell still gives players their own Agent's dice and Cell on every other page.

**New-Agent onboarding.** Finishing the character wizard, or importing an Agent onto the sheet (including Friendly's "Make this my Agent"), arms a **clearance briefing**: the first time the player then leaves the sheet, a green terminal types out the five tenets (our own wording, not the rulebook's) and asks `CAN WE CALL ON YOU? [Y/N]`, answered by typing or tapping the letter. A plain line on top says the Agent is saved and the briefing happens once. **Y** records it on the Agent File and opens the Agent's era photos to take the Face Plate; once a photo exists the next step offered is the Field ID. **N**/Escape puts it off until they next leave the sheet.

### Agent File (the character sheet)

Since v2.7.0 the Agent File paper (`assets/agent-paper.js`/`.css`, rules in `assets/agent-rules.js`, one live session per Agent in `assets/agent-live.js`) is a sheet to play from, on the notebook's Agent File page and on Agent Hub alike. Every change saves straight to the Agent's `characters/{code}` document, in the same format the old sheet uses, so A-Cell, Friendly and the old sheet still read it.

Since v2.8.0 it reads in five numbered parts — **1 Statistics, 2 Skills (with Find a skill…), 3 Psyche (Bonds, Motivations, Mental Disorders, Sanity adaptation), 4 Combat & gear, 5 Record (Incursion, Operations)** — with jump buttons under the vitals. Their headings take one of three looks, picked per device in the notebook's Settings → Agent File look: **Typed form** (default), **Folder tabs** or **Rubber stamps**. Appearance (with the physical description), Era photos and the Cell are drop-downs beside the photo rather than parts of the sheet; in the notebook they're folds under the photo, Era photos showing the plates with a link to make them on Agent Hub.

- **Vitals:** HP, WP, SAN and BP in framed boxes with − / + below.
- **Sanity:** **Roll SAN** is the d100 test against current SAN, and the Handler decides what follows. **SAN loss ▾** applies the loss the Handler announces (a number or dice, and Violence / Helplessness / Unnatural) without a test of its own. Full-page post-its follow as needed: a disorder that triggers on a loss of 2+, temporary insanity at 5+ (with a Projection option), Breaking Point (pick the new disorder; BP resets to SAN − POW), SAN 0, and adaptation on a kind's third incident (Violence: −1D6 CHA and the same from each Bond; Helplessness: −1D6 POW).
- **Skills:** tap to roll. A failed roll marks the skill in bold red until **Roll improvements** (+1D4 to each marked skill, through the Dice Roller).
- **Adding things in play:** Bonds (score − / +, **+ Bond**), Motivations (rolled or written), Mental Disorders, incidents, weapons (roll skill and damage), gear from the equipment catalog, wounds.
- **Cell ▾:** the initiative list, highest DEX first with KIA Agents last; tap a member for their card (photo, profession, cover, HP/WP/SAN/BP).
- **The paper wears as SAN falls** (since v3.1.0; `assets/agent-wear.css`, built by `scripts/agent-wear/build.py`). Clean at 50+, then a stage per ten points: grain and faint yellowing (49–40), a fold and foxing (39–30), a coffee ring (29–20), a water stain (19–10), the first blood and the page's own edge torn (9–1), blood spatter (0). It covers the whole page the file sits on, kept light enough to play from even when INSANE; since v3.2.0 its strength rises point by point with SAN (49–40 1–5%, 39–30 6–10%, 29–20 11–25%, 19–10 26–50%, 9–0 51–100%). From SAN 9 an **INSANE** stamp sits on the photo and name, worn and patchy, filling in from SAN 5 to solid at 0. Each **Mental Disorder** gets a small rubber stamp (red, violet or blue-black ink) scattered over the header, never on a button, the name or the vitals, always in the same spot. A new stage fades in, and a new disorder's stamp comes down with a thump (no motion with reduced motion). Agent Hub and the notebook only; A-Cell stays clean. Settings → "Paper wears as SAN falls" turns it all off on that device.
- **A Bond at 0** is struck through in red (the Agent File, the read-only paper, A-Cell's dossier); + brings it back.
- **SAN 0 is marked like KIA:** the Agent's name is struck through (Agent Hub's tab and header, the Agents menu, the Cell list in red, A-Cell's Cell cards, dossier and Sheet) with a small **INSANE** stamp beside it, live the moment SAN reaches 0 in play.
- **Edit** works on a copy. It unlocks stats, every skill (0% included), the specialties with their drop-downs and own skills, BP (− / + step by POW), personal data, the existing Bonds/Motivations/Disorders/weapons, the description and distinguishing features. **Save** shows the changes and a short Oath: **Y** files them, **N** goes back to editing with nothing lost.

Design and every feedback round: `docs/field-notes-widget/SPEC.md`.

### Table Radio (shared music widget)

`assets/table-radio.js` is the engine included on every player-reachable hub page that keeps a player "tuned in" to whatever the Handler is broadcasting from A-Cell's Music tab, staying loosely in sync as players move between pages via a server-stamped `started_at` timestamp every device reads. Backed by a live Firestore listener on `radio/{channel}` (it began as an Apps Script addition before the Sheet was retired). Players tune it from the Field Notes notebook's radio; its own floating pill now shows only on A-Cell.

**iPhone/iPad:** Safari plays nothing until the player has tapped the page once. After that first tap, new tracks and sound effects start by themselves, because the widget reuses `<audio>` elements a tap has unlocked. Any later tap anywhere, including inside the hub shell's content frame, also starts anything that was refused and routes the sound through Web Audio, the only volume control iOS honours. (See `BUGFIXES.md`, "Table Radio silent after the Storage CORS config".)

A soundboard on A-Cell's Music tab layers **7 ambient loops** (toggled
on/off per channel) and **24 one-shot stingers** (grouped Screams &
Laughter / Impacts & Weather / Bells, Rhythm & Texture / Creatures &
Voices) under the main
track — real recorded SFX (`assets/ambient/`, `assets/stingers/`), both
mirrored onto the same `radio/{channel}` Firestore doc Now Playing
lives on so every tuned-in player's widget picks them up instantly. A
Handler-draggable seek slider on the same tab lets the Handler jump the
current track to a new position; players only ever see a **read-only**
progress bar, so nobody can scrub their own copy out of sync.

An earlier attempt at ambient/stingers was built, tested, and then
deliberately abandoned before ever merging to `main` — the
procedurally-synthesized audio didn't sound convincing (only gunshot
variants were usable). See
`design-graveyard/table-radio-audio-soundscape`'s own `RETROSPECTIVE.md`
for the full account; its own recommendation to use real recordings
instead of synthesis is what the current, shipped version above is
built on.

### Friendly pregens

`friendly/pregens.json` is built from the Handler's fillable DD Form 315 pregens (the Arc Dream *Agent Dossiers* PDFs) in two steps, both in `scripts/pregens/` (see its README): `extract.py` reads each PDF's form fields and reports what the sheet leaves blank; `build.js` fills those blanks — name, sex, age/DOB, nationality, employer, education, physical description, distinguishing features, Bond names, Motivations — with the same tables the Creator's Random Bio / Random Motivation use, seeded per sheet, and finishes each sheet the way its own notes say ("Choose two from the following skills…", "Bonus skill points: Add +20% each to any six skills"). All 62 Dossiers ship; the picker groups them into six categories and has a one-tap "Hand me a dossier". The PDFs and the raw extract stay out of the repo (the site is public); only game numbers plus generated flavour are published.

### Offline support (PWA)

`manifest.json` + `sw.js` make this installable to a phone's home screen and usable at the table with no signal. `sw.js` runs a stale-while-revalidate strategy over the static app shell (every page, script, stylesheet, and icon listed in `SHELL_FILES`) — instant load from cache, refreshed in the background for next time — while deliberately leaving every Apps Script/backend call alone, so it never serves stale campaign data offline and calls it a feature. `CACHE_NAME` gets bumped on every shell file change so returning visitors aren't stuck on old JS. One real constraint worth knowing: iOS disables `window.alert()`/`confirm()`/`prompt()` entirely inside a home-screen-installed (standalone) PWA, so this app avoids native dialogs in favor of real in-page UI (inline inputs, `window.dgConfirm()` in `assets/field-notes.js`) wherever a flow needs to work standalone, not just in a normal browser tab.

### Appearance from the character sheet

Since v3.2.0 the Agent's Appearance brief fills its empty fields from their saved character sheet when the Agent File opens (`afCarryFromCharacter_` in `assets/agent-file.js`): sex, age range and nationality, a build from STR+CON, and clothes that fit the profession (from the Appearance generator, `assets/appearance-gen.js`). Carried-over fields are locked against the Random Agent Generator, so a reroll can't overwrite what the sheet already says. An Agent with a saved sheet but no brief at all gets one made from it the first time any page looks for it. The rest of how the Agent looks comes from New Recruit's Profiling step or the Appearance brief on Agent Hub.

Appearance counts as "done" only once every field the brief marks required has a real value; until then the Agent's tab shows it open, with how many details are left (and a callout under Play), whatever's already known filled in and locked, and the era photos wait -- they're made from it.

### Bringing an Agent in

New Recruit's start screen (Agent Hub, **+ New Recruit**) has one drop zone that takes any of these and works out the format itself (`assets/agent-import.js`), then walks through the wizard's review steps with everything the file carried filled in:

- **Kappa Black** `.toml` (a hand-rolled parser for exactly the flat subset [Kappa Black](https://www.kappablack.com/) exports; no Sex field, so that's entered by hand) and its `.json`, which is a Foundry VTT actor.
- **Foundry VTT** actor `.json`, and this site's own saved-character `.json`.
- **DD Form 315** `.pdf` (`assets/sheet-io/pdf-export.js`): this site's own exported sheets and official pregenerated Agent PDFs, whose form fields are the same.
- **Google Sheets** `.xlsx` (`assets/sheet-io/sheets-import.js`): the template the old sheet exported, including a copy edited in Google Sheets and downloaded again.
- The old sheet's **printable** `.html`, which carries its Agent inside.
- A **Friendly** pregen, or an **Agent Code** already on file.

None of them recovers everything (specialty instances, weapon rows and full Bond detail may need entering again).

### Saving

The Agent File saves the character to Firestore (`characters/{code}.character_json`) as it's played, a moment after each change (`assets/agent-live.js`), and Edit mode saves on the Oath's Y. Any device opens the same Agent by its code (`agent-hub.html?code=CODE`, or New Recruit's *Load by Agent Code…*) or by Cover Identity below. The notebook's Settings → Export builds a DD Form 315 PDF from the saved character.

### Agent Roster

A **persistent, multi-agent roster** in this browser (`localStorage`'s `dg_agent_roster`) — every Agent made, saved, opened by code or pulled in by Cover Identity on this device, with photo/name/code/codename/demographics/era. Agent Hub renders it as its folder tabs. (The old Agent Portal's slide-up roster drawer went with the portal.)

### Cover Identity

The roster above is purely local to one browser — until now, a fresh device or a cleared browser had no way to find a player's existing Agents at all beyond knowing their exact Agent Code by heart. **Cover Identity** (your real name, not the Agent's — reuses the `player_name` field already on the character sheet's Biography, now doubling as a lookup key) fixes that: enter it once in the field at the top of `agent-hub.html` and every Agent tied to that name — character sheet, Agent File, or both — replaces this browser's *claimed* roster entries with exactly that set. Remembered locally afterward, so a returning visit refreshes automatically with no retyping.

An Agent tied to a *different* `player_name` won't show up here even if this browser touched it before — that's the point, so one device can be handed between players without their rosters bleeding into each other. Since v3.2.0 the lookup keeps only that name's Agents: an Agent with no `player_name` yet comes back by its code (`?code=CODE`), or once the player fills in their Player Name or a Handler backfills it from A-Cell's Sheet tab.

A bare name match, deliberately — no PIN, no auth. Real access control (so players can't pull down agents that aren't theirs just by guessing a name) is tracked as its own separate, later roadmap item below, not bundled into this.

(History — now a Firestore query on `player_name_lc`.) Needed a small, additive Apps Script change at the time: a `player_name` column on both the `Characters` and `Delta Green Briefs` sheets, and a new `find_by_player_name` lookup action — see `backend/Code.gs`. Degrades gracefully (shows "No Agents found") until that's pasted in and redeployed, same as every other backend addition here.

Also: the Agent's own printable fake-ID-card feature used to be called "Cover ID" — renamed to **Field ID** throughout (buttons, tabs, `dg-id-creator.html`) to free up "Cover Identity" for this, since the two are unrelated concepts (one's the Agent's in-fiction alias, the other is the real player behind the keyboard).

### Backend

**Retired as the data store (v97, see Firebase / Firestore below)** — after the one-time migration it only serves the Drive image proxy for old `gdrive:` links. The Google Apps Script + Sheets project lives outside this repo (Apps Script has no git integration of its own) — `backend/Code.gs` is a checked-in mirror of its full source, kept in sync by hand: edit it here, then paste the whole file over the live project's `Code.gs` in the Apps Script web editor and redeploy. Every page degrades gracefully when a given action isn't live yet (JSONP calls just fail silently), so this repo's frontend can stay ahead of the deployed backend without breaking anything.

### Firebase / Firestore

The app's backend. It was layered on top of Sheets over several migration passes and replaced them: a live Firestore read is both faster and immune to the JSONP-timeout class of "could not load X" failures a single-shot Apps Script round trip was prone to under a weak connection.

- **Everything, as of Code.gs v97 (2026-09-30): the Sheet is retired.** Every page reads and writes Firestore directly — characters, Agent Files, Cells and membership, Evidence and Operations, Notes, Notes identities and "seen" marks, handout notes, Table Radio and its Cue List, the soundboard, Track Library, dice rolls, A-Cell's Sheet tab and Recently Deleted, and the error log. Player-side calls share `assets/dg-store.js`; A-Cell's Handler actions are its own `window.dgAcellApi`. AI prompt/image generation runs as Cloud Functions (`functions/index.js`); `generatePrompt`, `generatePlateImage` and `dailyBackup` were only actually deployed on 2026-10-01 — until then Generate failed with "internal" (see `BUGFIXES.md`). Since v2.2.0 a failure shows its real message under the prompt and lands in `functions:log`; the functions' service account needs `roles/datastore.user` and `roles/storage.objectAdmin` (FEATURES.md §12). Like the rules below, functions deploy by hand: `firebase deploy --only functions:NAME`. The only Apps Script call left is the Drive image proxy (`imgdata`) for old `gdrive:` photo links. Going live takes the one-time steps in `docs/firebase-migration/SHEET-RETIREMENT.md`.

**Storage CORS (`storage.cors.json`).** The Storage bucket needs a CORS config allowing this site's origin before Table Radio can control the main track's volume on iOS (issue #39): the widget only routes a track through Web Audio (the one volume control iOS honours) after the track's host has answered a CORS check, and plays it the plain way otherwise. It is set once, by hand, on the bucket -- not by `firebase deploy`: in Google Cloud Shell, `gcloud storage buckets update gs://dg-app-b3447.firebasestorage.app --cors-file=storage.cors.json`. No code change is needed afterwards; listeners pick it up on their next page load. The Table Radio debug line shows `route=webaudio` once it's working (`route=element` before).

`firestore.rules`/`firestore.indexes.json`/`storage.rules` in this repo are, like `backend/Code.gs`, **mirrors only** — a `git push` never deploys them; that needs `firebase deploy --only firestore:rules` (or the matching target) run by hand from a checkout that actually has the change. A stale live deploy of an otherwise-correct-looking rules file is a real, previously-hit failure mode (see `BUGFIXES.md`'s Live Rolls entry) — when a Firestore permission error doesn't match what's in this repo's `firestore.rules`, suspect a missed deploy before suspecting the rule itself.

**Handler authentication is now a single prompt, full stop.** Typing the real Handler password into A-Cell's own black-terminal Clearance gate both clears that gate AND signs into Firebase in the same action, calling the `handlerLogin` Cloud Function directly; that ID token (carrying a `handler:true` custom claim) is the only Handler credential anywhere — Firestore's rules check it via `isHandler()`, and every remaining Handler-gated Apps Script action verifies the same token server-side via `verifyHandlerIdToken_()` (Identity Toolkit's `accounts:lookup` REST endpoint, since Apps Script can't run the Admin SDK). There is no second password box anywhere in A-Cell — that used to be a separate, real-credential prompt right below the header, folded into the gate itself on request. The Clearance gate's own OLD public flavor password (MASTICATE, purely client-side, no real security) is gone from A-Cell entirely; the old separate Apps Script session (`handler_login` POST action, opaque `dg_acell_session` token, `requireHandlerSession_()`/`HANDLER_SESSION_TTL_SECONDS`) is also gone — Code.gs never sees the raw password at all now. See `BUGFIXES.md`'s "Handler auth unification" and "Clearance gate IS the Handler login" entries for the full before/after.

Rough priority order, cheapest/highest-value first:

2. ~~Skills & weapons.~~ Done.
3. ~~A real percentile roller.~~ Done — the Dice Roller (`assets/dice-roller.js`), on the notebook's Dice page.
4. ~~Live-play HP/SAN tracking.~~ Done — the Agent File's HP/WP/SAN/BP boxes with − / + (since v2.7.0).
5. ~~Handout/clue log.~~ Done, then grown into a full **Evidence Locker**: A-Cell's Evidence tab files items into per-Operation folders within a Cell, stages them behind a Released toggle, and can restrict a released item to specific Agents — mirrored read-only into each Agent's hub view (still labeled "Handouts" there) with private per-Agent notes.
6. ~~Offline/PWA support.~~ Done — see Offline support above.
7. **Access control.** A-Cell is gated behind a shared password; individual Agent dossiers/character sheets are still reachable by anyone who has the code, and Cover Identity (above) is a bare name match with no PIN or auth — none of this is tied to real per-player identity yet. Partial progress: Firestore's own rules now enforce a real `isHandler()` custom claim (see Firebase/Firestore above) for Handler-gated collections, and per-Agent Firestore reads (Evidence, etc.) go through a real per-Agent Firebase Auth token (`exchangeAgentToken`) rather than a bare code — but this only covers the Firestore-backed surfaces, and the Apps Script side (still most of the write path) has no equivalent.
8. ~~Multi-source character sheet import + a roster to browse them.~~ Done — see Import Agent and Agent Roster above.
9. ~~Deploy the Cloud Save Apps Script addition.~~ Done, and since superseded: characters save straight to Firestore.
10. ~~Shared/private session notes.~~ Done — `notes/`, one shared+private notebook per Cell (see the table above): Timeline, Pin, Tags, cross-tab search, and a per-viewer Plain Fonts toggle.
11. **Surface Evidence inside Notes.** The Evidence Locker's own richer per-Agent view (an always-visible "Evidences" sidebar section with an unseen-item indicator, a detail view, and per-Agent remarks on an item) is planned but not yet built — right now Evidence only has A-Cell's management UI and agent-hub.html's simple read-only mirror.
12. ~~**Phase 2 (Sheets removal): Evidence Locker content CRUD off Apps Script, straight to Firestore — blocked.**~~ Done in v97: A-Cell writes Evidence straight to Firestore and recomputes `visible_to` from the Firestore Cell's members itself, so the Sheet-scan problem that blocked it no longer exists. Every other "clearest remaining partial migration" surface has moved to direct Firestore writes (see Firebase/Firestore above); Evidence content (`create_evidence`/`update_evidence`/`delete_evidence`) was next in line and was actually written and working in isolation, but shelved before shipping: `recomputeEvidenceVisibleToForCell_()` (called whenever a Handler adds/removes a Cell member) recomputes every Evidence item's `visible_to` by scanning the **Evidence Sheet**, not Firestore — if Evidence writes stopped hitting Sheets, any item created afterward would be invisible to it forever, silently going stale the next time that Cell's membership changed. Needs a real Firestore *query* capability in `backend/Code.gs` first (a `:runQuery` REST call, converting its typed-value response back to plain JS — the existing `firestoreDualWrite_`/`firestoreDualPatch_`/`firestoreDualDelete_` helpers only ever address one document at a time by id), untestable end-to-end through this repo's own Playwright suite (it mocks Firestore, not a real GCP project), so worth building and testing as its own piece of work rather than bundling it into the next batch. See `BUGFIXES.md`'s "Phase 2 (Sheets removal), investigated but deliberately NOT migrated: Evidence Locker content CRUD" for the full account.
