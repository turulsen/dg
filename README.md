# Delta Green Agent Hub

Player-facing tools for a Delta Green campaign, published as a static site via GitHub Pages.

**Live site:** enable GitHub Pages on this repo (Settings → Pages → Deploy from branch → `main` → `/ (root)`) and it'll be served at `https://<your-username>.github.io/dg-campaign/`.

## What's here

The hub landing page (`index.html`) links to two tools, plus a **"Continue
Playing" panel**: if this browser has a saved agent (`localStorage`'s
`dg_last_agent`, written by both the Agent Portal's Cover form and
`stats/`'s Export to Agent File / Open Agent File buttons), the hub shows
that agent's name, code, codename, last-updated date, and photo (if one was
uploaded) right at the top, linking straight to the Agent Portal's Agent
File tab for it. It's hidden entirely for a fresh browser with no saved
agent yet, rather than showing an empty preview.

| Page | Purpose |
|---|---|
| `stats/index.html` | Full Delta Green character creator — point-buy or dice-roll stats, 18 professions with contextual skills, bonus skill points, random bio generation, Bonds, equipment loadout, a dice-roller widget, save/share, and printable/Foundry VTT export. **Six visual themes**, including a dedicated "Live Play" mode with a sticky HP/WP/SAN tracker bar for use at the table — **all six work on a phone**, see Mobile below. Ported wholesale from [pigeon-labs-stack's DELTA-GREEN-STATS](https://pigeon-labs-stack.github.io/DELTA-GREEN-STATS/) — see Attribution below. Auto-saves to this browser as you go (so it remembers where you left off), and has an **Open Agent File** button above the theme selector to export the current character and jump straight to the Agent Portal's Agent File tab for it — see below |
| `dg-agent-portal.html` | The place to come back to. Three tabs on one Agent: **Cover** (physical description brief + AI portrait prompt + printable dossier), **Agent File** (load an existing agent by its Character Code across sessions/devices), and **Cover IDs** — the "Cover ID Fabricator," a native in-page tablet UI: pick a cover agency (FBI, DEA, ATF, Secret Service, ICE, CBP, NCIS, FinCEN, USPI, NYPD, county sheriff, the fictional M-EPIC, or a Delta Green Directorate credential) and an era (90s/00s/10s/20s), and it renders a historically-styled credential card live, with an agent-code importer and PRINT/EXPORT. Every rendered card — on-screen and in the printed/exported version — carries a diagonal "PROP — NOT A GOVERNMENT DOCUMENT" watermark, so a card is still unmistakably a game prop if it's ever seen outside the game. A slide-up **Agent Roster** (trigger at the bottom of the screen) remembers every agent submitted or loaded in this browser and lets you switch between them — see Import Character below. Backed by a Google Apps Script + Sheet |

`dg-id-creator.html` still exists as its own standalone file (a simpler, paper/dossier-styled cover-ID card generator, with its own `DG-` base64 save codes), but it's no longer linked from the hub or the Agent Portal — the Cover IDs tab's native Fabricator superseded it. Kept in the repo for now rather than deleted.

All pages are static HTML/CSS/JS with no build step. `stats/` is the one exception to "single self-contained file" — it's a direct, unminified copy of pigeon-labs-stack's own multi-file layout (one HTML file, one stylesheet, twelve `.js` files), kept that way deliberately so it stays diffable against upstream.

### Export to Agent File

`stats/`'s "Export to Agent File" button (`stats/agent-portal-export.js`) sends a finished character to the Agent Portal using the **exact same submission path** the Portal's own Cover form uses — same Apps Script endpoint, same field names, same `PREFIX-XXXX` code format. It's not a new backend integration; it's this page filling out that form programmatically. Name, age range, sex, nationality, and profession carry straight over from the character's Biography; build and outfit are derived automatically and sent quietly in the background, since they already feed the Portal's AI portrait-prompt generator:

- **Build** — from STR+CON, reusing the same tiered word pools (`bioData.buildDescriptors`) the Creator's own "Random Bio" feature uses, so an above-average-strength Agent gets a build description to match.
- **Outfit** (jacket/shirt/trousers/footwear) — a plausible default per profession (`PROFESSION_OUTFIT` in that same file), e.g. a physician gets a lab coat and scrubs, a special operator gets tactical gear.

Everything else about physical appearance is left blank, same as any new agent — the Cover tab in the Portal stays the place to fill in or edit the rest. The exported agent's code is saved to this browser's `localStorage` (`dg_last_agent`) so the Agent Portal picks it up automatically if opened next in the same browser. (Campaign era/decade isn't part of this bridge — the Agent File's era selector stays a manual one-time choice per agent, since `stats/` characters carry no era of their own to derive a default from, and a wrong guess would leave a stray era stacked on the file.)

There are two ways to trigger this from `stats/index.html`:
- **"→ Open Agent File"**, the button above the theme selector (replacing the old paragraph that mentioned Foundry VTT — this hub doesn't use Foundry, so that was just noise). One click exports the current character *and* navigates straight to the Agent Portal, landing directly on the Agent File tab with that character already showing, not the Portal's default Cover tab.
- The **"→ Export to Agent File"** button further down, in the save/share bar, for exporting without leaving the page.

This bridges `stats/` → Agent Portal one-way. It does *not* unify the three separate code/save systems described in Roadmap item #1 below — the ID Creator's own code format is still separate.

### Mobile

`stats/` originally only worked cleanly on a phone in its dedicated "Mobile" theme — the other five (X-Files, Modern, Son of Sam, Field Notes, Live Play) genuinely overflowed horizontally, since pigeon-labs-stack built them desktop-first. Fixed via a viewport-width-gated addition at the bottom of `stats/styles.css` (not scoped to any theme, so it changes nothing on desktop). Root cause of most of it: browsers give every `<fieldset>` a default `min-width: min-content`, so it refuses to shrink below its widest unbreakable content no matter how well the layout inside it collapses — plus a few genuinely fixed-width grids (the skills list's `80px` column gap, biography fields' `160px` label column, the equipment picker).

Live Play was the trickiest, since its full character sheet mirrors a printed form (percentage-width table columns, side-by-side sub-sections) rather than being built for a phone at all. An earlier version of this fix kept the sheet at its natural width and let it scroll horizontally within its own box, "like panning a PDF" — in practice that left Nationality/Sex/Age/Education and the entire Bonds table sitting off-screen to the right with no visual cue there was more to scroll to, which real usage on a phone confirmed was worse than losing some paper-form fidelity. It now genuinely reflows below 700px instead: the Personal Data table's `<table>`/`<tr>`/`<td>` switch to block display so each field stacks as its own full-width row (with a matching `height: auto` override, since the base stylesheet fixes every LP table row to 28px for column alignment — correct for the single-line Statistics/Bonds/Derived-Attributes tables, wrong for a row that now stacks seven fields), and the Stats+Bonds / Derived+Motivations / Physical-Description+Incidents side-by-side pairs stack vertically instead of sitting 44%/flex-1 next to each other. The Applicable Skill Sets grid needed `min-width: 0` (not just fewer columns) since a CSS grid's implicit `minmax(auto, 1fr)` track sizing was using each skill table's unwrapped-text min-content width regardless of column count. The sticky HP/WP/SAN/BP tracker bar and the Dice Roller widget (which auto-expands when Live Play is selected) needed their own fixes too — the tracker bar was cramming 6 items into one row illegibly (now 4, with the two roll-shortcut buttons dropped as redundant with the Dice Roller/skills table on narrow screens), and the Dice Roller was a fixed 270px panel floating off to one side (now a full-width bottom sheet, and no longer auto-expands over that content on a phone in the first place).

### Import Agent (one button, any format)

Picking the right one of five format-specific buttons was the cumbersome part — a player just wants to hand over their file. `stats/index.html` now has a single **"Import Agent"** drop zone right at the top of the page (next to Open Agent File), before any Advanced panel needs opening: drop a file, or click to browse, and `importAgentAuto()` (`stats/scripts.js`) figures out the format itself and routes it to the matching importer below — no new parsing logic, just the routing in front of what already existed. Detection is by file extension first (`.toml`, `.json`, `.pdf`, `.xlsx`, `.html`), falling back to sniffing the actual bytes/content for a file dropped in without one (common from a mobile "Share" sheet) — a `%PDF` header, a zip signature for `.xlsx`, `<` for an HTML sheet, `{` for JSON, or a bare `key = value` line for TOML. A `.json` file is further split between this site's own native save format (`downloadSheet()`'s `v:1` state, applied via `applyState()` directly) and a Foundry VTT actor (applied via `applyImportedAgentData()`) by checking for the `v:1` marker, since both are valid, common `.json` files a player might hand over. The original format-specific buttons are still in Advanced below, for pasting text directly or troubleshooting a file this doesn't recognize.

Several agents in this campaign were built on other tools before this hub existed. `stats/`'s Advanced — Export & Import section (same place the Foundry VTT / Printable Sheet / Google Sheet exports already lived) has import counterparts for the main ones, all reachable through the one-button importer above:

- **Import from PDF Sheet** — already existed as a pigeon-labs-stack feature, but was silently broken here: the fillable PDF template it needs (`stats/assets/Delta-Green-RPG-Character-Sheet.pdf`) was never copied over when `stats/` was ported, so every export/import attempt 404'd. Restored from upstream. Turns out this also makes it work on **official pre-generated Delta Green Agent PDFs** from published scenarios (e.g. an `Agent's Handbook`-era handout) — checked by diffing the AcroForm field names of a real one byte-for-byte against the blank template, and they're identical, so no separate parser was needed for "the official PDF" as its own source.
- **Import from Google Sheet** (`stats/sheets-import.js`, new) — the counterpart to the existing Export Google Sheet button, whose own template asset (`stats/assets/Delta-Green-character-sheet-template.xlsx`) had the same missing-file problem, also restored. Reads the same fixed cell addresses the export writes, and separately resolves `xl/sharedStrings.xml` — not just the inline-string cells the export itself produces — since the realistic workflow is export → upload to Google Sheets → edit there → download again, and Google Sheets commonly rewrites those cells to shared-string references on save.
- **Import from Kappa Black** (`.toml`, added straight to `stats/scripts.js` — `parseSimpleTOML()` / `convertKappaBlackToAgentData()` / `importKappaBlackTOMLToEditor()`) — Kappa Black's own flat TOML export, since kappablack.com and its GitHub source were both unreachable from this hub's dev sandbox to derive the schema any other way; built once a real export sample was shared directly. No TOML parser was already on the page (and adding one would mean a new CDN dependency this app otherwise avoids), so it's a hand-rolled parser scoped to exactly the subset Kappa Black uses — flat scalars, `[section]` stat tables, and `[[array]]` tables for bonds/skills/special training/weapons — not a general TOML parser. The parsed file is reshaped into the same object shape a real Foundry VTT export uses and handed to the same `applyImportedAgentData()` Foundry JSON import already relies on, so profession/skill/bond/gear handling is shared code, not a second copy of it. **Limitation:** Kappa Black's TOML has no Sex field (unlike its own Foundry JSON export, which does) — needs manual entry after import.
- Kappa Black's **JSON** export is Foundry VTT actor JSON, confirmed against a real user export — it already works via the existing **Print from Foundry .json** import once the profession-resolution fix above landed, no separate code needed. Its **printable PDF** export wasn't checked against the DD Form 315 field schema; try **Import from PDF Sheet** above, but it may need the same investigation the official PDFs got if the fields don't line up.

All of these land through the exact same `dgSaveLoad.applyState()` / `applyImportedAgentData()` path `stats/`'s own Printable-Sheet-HTML and Foundry-JSON imports already use, so a successful import behaves like any other loaded character — auto-saves, exports to Agent File, etc. — normally. Like the PDF importer, none of these recover *everything* (specialty skills, weapon tables, and similar detail may need re-entry) — see each button's own description in the Advanced panel for specifics.

### Cloud Save

Every import above is still a file changing hands — fine for a one-time move, cumbersome if you want a character to just follow you between a laptop and a phone at the table. `stats/cloud-sync.js` adds an **automatic** save on top of the existing Apps Script backend (the same one Cover-form briefs already go to), keyed by an Agent Code — no different a code from any other in this hub, just a new use for one:

- **Auto-starts on its own** — the first edit made after a real name is entered mints a code (shown in the status line) and pushes immediately; every edit after that debounces another push, so the cloud copy stays current with no button to remember — this is the actual answer to "why can't Live Play just save dynamically," and to "what if a player forgets to turn it on" (nothing to turn on). It only triggers once a real name exists, the same "is this actually a character yet" threshold `agent-portal-export.js` uses elsewhere, so idle theme-switching or point-buy fiddling on a fresh page doesn't mint a throwaway row in the Characters tab for every casual visitor.
- **☁ Start Cloud Save** still exists for one case: starting immediately even before typing a name.
- **☁ Load by Code** pulls a previously cloud-saved character back down by its code, on any device/browser, and re-activates syncing under that code going forward.
- **No Stop button.** An earlier version had one, but once syncing is fully automatic, "stop" isn't a real setting — any edit could silently re-provision a cleared code and resume it, which would have needed its own persisted opt-out flag just to make Stop mean anything. A toggle nobody can predict the state of is worse than not having one, so it was removed rather than patched: once a character is named, syncing it is just how the page behaves now, the same way local autosave already always has been.

Uses the exact same `APPS_SCRIPT_URL` and `fetch(..., {mode:'no-cors', keepalive:true})` fire-and-forget pattern `agent-portal-export.js`'s Export to Agent File already uses, just a new `action` (`save_character` / `?action=load_character`) on the same endpoint — not a new backend integration from the client's point of view. It needed a small, purely additive change on the Apps Script side too: a new `Characters` tab (one row per Agent Code, upserted rather than appended, so repeat saves overwrite instead of piling up duplicates) alongside the existing `Delta Green Briefs` tab, in the same spreadsheet file — see `character-cloud-save-addition.gs` (handed over separately, not committed to this repo since it's Apps Script, not something this static site serves). **Deployed and confirmed working** as of this writing. Until an Apps Script deployment has this addition, Cloud Save fails silently/returns "not found," the same graceful-degradation this app already has for every other Apps Script call — which is what made it safe to ship ahead of that step.

### Agent Roster

`dg-agent-portal.html` now keeps a **persistent, multi-agent roster** in this browser (`localStorage`'s `dg_agent_roster`) — a slide-up drawer (trigger button at the bottom of the screen) listing every agent that's been submitted via the Cover form or loaded by code here, with photo/name/code/codename/demographics/era. Click a card to switch to that agent, delete individual entries, or export/import the whole roster as a `.json` file. This is what answers "see and navigate between the uploaded character sheets" for a Handler checking multiple players' briefs, or a player who's made more than one agent over time — ported from the project's `Dev` branch alongside the Cover ID Fabricator earlier.

## Roadmap ideas for a fuller Agent Hub

Rough priority order, cheapest/highest-value first:

1. **Unify the character-code system.** There are still *three-and-a-half* separate identity/save systems that don't talk to each other: the Agent Portal's `PREFIX-XXXX` codes (Apps Script-backed), the now-unused `dg-id-creator.html`'s `DG-` base64 codes, `stats/`'s own save/share-link system (localStorage + a TinyURL-shortened link), and now `stats/`'s **Cloud Save** code (also `PREFIX-XXXX`-shaped, same backend, but tracked under its own `dg_stats_cloud_code` key, independent of whatever code Export to Agent File separately mints for the same character). The **Export to Agent File** button bridges `stats/` → Agent Portal one-way (using the Portal's own code format), and the Cover IDs tab's Fabricator imports agents by the Portal's own `PREFIX-XXXX` code too (same Apps Script query as the Agent File tab) rather than adding a fourth format — so the real outliers left are `dg-id-creator.html`'s orphaned `DG-` codes and Cloud Save's separately-tracked code. Still the single biggest gap, but a smaller one than it was.
2. ~~Skills & weapons.~~ Done — `stats/` covers skills (full list + specialties), professions, and an equipment/weapon loadout picker.
3. ~~A real percentile roller.~~ Done — `stats/` has its own dice-roller widget (quick dice, custom rolls, roll-under-% checks) built in.
4. ~~Live-play HP/SAN tracking.~~ Done, sort of — `stats/`'s "Live Play (Field Notes)" theme has a sticky HP/WP/SAN/BP tracker bar and a full live character sheet. Cloud Save (above) now bridges it to the same backend the Agent Portal's dossier system uses, but as its own JSON blob in a separate `Characters` tab, not a unified record (see #1).
5. **Handout/clue log.** A shared, per-campaign log where the Handler drops handouts (pairs well with a "delta-green-handouts" style PDF workflow) and players can revisit them.
6. **Offline/PWA support.** Add a manifest + service worker so the hub works at the table without signal.
7. **Access control.** The Agent Portal already gates some content behind a character code; if players shouldn't see each other's dossiers, consider per-agent codes tied to real auth rather than security-by-obscurity codes.
8. ~~Multi-source character sheet import ("Phase 2") + a roster to browse them.~~ Done — see Import Agent and Agent Roster above. Official/pigeon-labs-stack PDF import, Google Sheet import, **[Kappa Black](https://www.kappablack.com/)** TOML/JSON import, a single format-agnostic Import Agent drop zone, and the Agent Roster are all live.
9. **Deploy the Cloud Save Apps Script addition.** `character-cloud-save-addition.gs` needs to be pasted into the live Apps Script project and redeployed before Cloud Save (above) actually persists anywhere — the client-side half is live and degrades gracefully until then.
